# Engineering Progress Report — 2026-10-08

**Client:** Gyile / GyLiber  
**Product:** GyLiber Security Intruder  
**Milestone:** v0.2.0 — integrity and authenticity  
**Status:** release candidate

## Executive summary

The project has advanced from v0.1.0's bounded, hash-sealed assurance loop to a cryptographically authorized assurance loop.

v0.2.0 introduces signed target/campaign authorization, signer roles, validity/revocation/rollback controls, evidence-signer preflight, and signed evidence-bundle manifests. The existing Target Gate, safety budgets, kill switch, IP-literal HTTP HEAD probe, PASS/FAIL oracle, and secure/vulnerable/fixed fixture proof remain intact.

This minor release is deliberately designed to be presentable to the client as externalized progress without pretending that production infrastructure or broad offensive capability has been completed.

## Demonstrable client progress

The client can now be shown that:

- an unsigned or tampered campaign cannot authorize execution;
- a signer must be trusted for the correct role;
- expired/revoked/rolled-back authorization fails closed;
- target/campaign identity is cryptographically bound to its envelope;
- the evidence signer is verified before the network probe;
- run-bundle file hashes are authenticated by a signed manifest;
- a modified bundle fails independent verification;
- dependency licenses and sources are enforced in the Security workflow.

A reproducible walkthrough is maintained in `docs/CLIENT_DEMO_v0.2.0.md`.

## Quality evidence before release

The complete v0.2 signing/operator branch passed:

- formatting;

- RustSec;
- CodeQL.

The dependency license/source policy passed independently before promotion into the permanent Security workflow.

The final release commit must repeat all normal CI/Security checks and the independent release-build/attestation path before the tag is created.

## Remaining manual governance work

Repository administration settings that are not available through the current connector remain explicit rather than guessed:

- secret scanning / push protection;
- branch/ruleset protection and required checks.

Independent cross-provider backup/restore proof and production key custody also remain open.

These do not block the synthetic/LAB v0.2.0 client release, but they block escalation to production/high-consequence operation.

## Client message

v0.2.0 is meaningful progress because it strengthens **who is allowed to authorize assurance work and who can authenticate the evidence**, without expanding the tool into uncontrolled scanning.

The next planned product capability is v0.3.0 synthetic authentication/session assurance.

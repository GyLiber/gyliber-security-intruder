## 1. Executive summary

The project has crossed an important engineering boundary: it is no longer only a collection of security-domain types and policies. An operator-facing command can now execute one controlled baseline assurance probe from end to end.

The implemented path is:

```text
strict JSON execution specification
        |
        v
target validation
        |
        v
kill-switch authorization
        |
        v
central execution budget
        |
        v
Target Gate + resolved-address policy
        |
        v
bounded IP-literal HTTP HEAD probe
        |
        v
typed PASS / FAIL oracle
        |
        v
metadata-only evidence record
        |
        v
SHA-256 integrity seal + verification
        |
        v
create-new JSON report + human report
```

This is the first operator-executable slice of the intended v0.1.0 closed loop. It remains deliberately constrained and is not production authorization.

## 2. Implementation delivered

### Repository and engineering controls

The repository currently includes:

- Rust 1.99.0 / Edition 2024 workspace configuration;
- committed dependency lockfile enforced by CI;
- formatting, compilation, strict Clippy, and workspace test gates;
- RustSec dependency auditing;
- CodeQL Rust security analysis;
- pinned GitHub Actions revisions;
- conventional commit history;
- repository security, contribution, design, requirements, implementation, and engineering-gap documentation.

### Target and network safety

Implemented controls include:

- explicit target identifiers and environment classification;
- scheme, host, and path allowlists;
- LAB/STAGING-only opt-in for private-network destinations;
- CANARY/PRODUCTION prohibition on private-network opt-in;
- resolved IPv4/IPv6 destination classification;
- denial of loopback/private/link-local/special-purpose destinations where policy requires;
- explicit denial of known cloud metadata endpoints;
- resolved-address authorization suitable for later DNS-rebinding protection;
- no normal arbitrary-target scanner command.

### Execution safety

Implemented controls include:

- global kill switch;
- target-specific stop state;
- campaign cancellation state;
- total-request budget;
- requests-per-second budget;
- concurrent-request budget;
- authentication-attempt budget;
- maximum execution-time budget;
- enforcement that the runtime budget exactly matches the enrolled target budget;
- request-permit lifecycle that releases concurrency on completion/drop.

### Bounded HTTP probe

The first real transport is intentionally narrow:

- HTTP `HEAD` only;
- enrolled IP-literal target only;
- hostname execution remains unarmed;
- automatic redirects disabled;
- automatic retries disabled;
- environment/system proxy inheritance disabled;
- response bodies are not read or retained;
- response header values are not retained;
- observed metadata is limited to status code, content length, and header names;
- TLS minimum is configured as TLS 1.2 for TLS connections;
- request/connect timeout derives from the centrally authorized execution budget.

### Evidence and reporting

The evidence/reporting path now provides:

- typed expected HTTP status;
- typed observed HTTP metadata;
- explicit PASS/FAIL verdicts;
- metadata-only evidence handling classification;
- deterministic header-name normalization;
- SHA-256 evidence digest with a GyLiber-specific domain separator;
- integrity re-verification before report rendering;
- human-readable run report;
- serializable JSON run report.

The SHA-256 digest is an integrity mechanism, **not a digital signature**. Cryptographic authenticity/signing remains a later capability.

### Operator CLI closed loop

The operator interface now includes:

```text
intruder baseline-run --spec <execution.json> --json-out <report.json>
intruder kill-switch-status
```

The baseline command does not accept a raw URL directly. The candidate URL is part of a strict JSON specification together with its enrolled target and explicit kill-switch snapshot, and it must still pass all runtime policy gates.

The specification rejects unknown top-level fields.

JSON report creation uses create-new semantics: an existing report path is not silently overwritten. The created file is explicitly flushed/synchronized before successful command completion.

## 4. Security posture of the current milestone

The current slice is designed to be useful without prematurely enlarging the attack surface.

It does **not**:

- accept arbitrary raw target URLs as a normal operator command;
- execute against hostnames;
- follow redirects;
- inherit ambient proxy configuration;
- retain response bodies;
- retain HTTP header values;
- contain production Command Center credentials;
- require a production database;
- provide malware, persistence, password cracking, credential stuffing, DDoS, or lateral-movement behavior.

The repository remains public, so all committed examples and fixtures must remain synthetic and non-sensitive.

## 5. Known limitations and intentionally unarmed capabilities

The following are not represented as complete:

- execution specifications and kill-switch snapshots are not digitally signed;
- there is no durable signed target registry yet;
- hostname/DNS execution is not armed;
- DNS resolution is not yet bound end-to-end to connection establishment;
- redirect re-authorization is designed but the first probe simply disables redirects;
- the secure/vulnerable/fixed fixture laboratory is not yet packaged as persistent project fixtures;
- the current operator loop executes one baseline probe, not a multi-probe campaign;
- the current evidence hash proves integrity only, not signer identity/authenticity;
- durable evidence/object storage is not yet configured;
- scheduled assurance is not yet enabled;
- release artifacts, checksums, provenance, and v0.1.0 tagging are not yet complete;
- production Command Center testing is not authorized by this milestone.

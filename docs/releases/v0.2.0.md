# v0.2.0 — Integrity and authenticity

**Release date:** 2026-10-08  
**Release class:** client-presentable minor release  
**Data posture:** synthetic/security-test data only

## Summary

v0.2.0 adds cryptographic authorization and evidence authenticity to the bounded assurance loop established in v0.1.0.

The main client-visible change is that target/campaign documents are no longer executable merely because they parse and satisfy policy. They must be signed by explicitly trusted Ed25519 identities with the correct role, validity state, revocation state, and revision floor.

Run bundles now include a signed manifest so their file digests can be tied to an authenticated evidence signer rather than relying only on unauthenticated SHA-256 integrity hashes.

## Added

- `intruder-signing` crate with deterministic canonical JSON and domain-separated Ed25519 envelopes;
- target, campaign, and evidence signer roles;
- key validity windows and revocation state;
- minimum target/campaign revision floors;
- envelope/payload identity checks;
- campaign envelope revision binding to `campaign_version`;
- evidence-signer preflight before network execution;
- signed evidence-bundle manifests;
- independent `intruder bundle verify` flow;
- key generation and LAB trust-bootstrap commands;
- target/campaign sign and verify commands;
- key-management and client-demonstration documentation;
- dependency license/source enforcement through pinned `cargo-deny 0.20.2`.

## Security tests

Automated tests cover successful signed authorization plus rejection of:

- payload tampering;
- wrong/untrusted signer;
- expired authorization;
- revoked signer;
- signer role mismatch;
- rollback below minimum revision;
- target/campaign identity mismatch;
- campaign revision mismatch;
- evidence file tampering;
- evidence private key that does not match the trusted public key.

The original secure → PASS, vulnerable → FAIL, fixed → PASS fixture triplet remains part of the full workspace test suite.

## Private-key handling

Generated private-key files use create-new semantics and Unix mode `0600` where supported. Private key material is redacted from debug output and zeroized in designated memory buffers/types.

Production KMS/HSM integration is not claimed in this release.

## Supply-chain controls

The Security workflow now requires:

- RustSec dependency audit;
- dependency license/source policy;
- CodeQL Rust analysis.

The license policy uses a crate-specific `CDLA-Permissive-2.0` exception for `webpki-root-certs 1.0.9`, the transitive TLS root-certificate dataset. Unknown registries and Git dependency sources are denied.

## Deliberately unarmed

v0.2.0 does not add broader offensive capability. The following remain unarmed:

- hostname/DNS execution;
- redirect following;
- authentication/session campaigns;
- authorization/API campaign families;
- detection/containment/recovery integration;
- scheduled continuous assurance;
- production Command Center authorization;
- confidential durable evidence storage;
- production key-custody/KMS integration.

## Release trust

Publication is permitted only after the exact release commit passes normal CI and the complete Security workflow, then independently rebuilds/tests in the release workflow, produces a CycloneDX SBOM and SHA-256 checksums, and successfully creates build-provenance and binary-SBOM attestations.

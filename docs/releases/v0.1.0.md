# v0.1.0 — Closed-loop safety foundation

GyLiber Security Intruder v0.1.0 is the first working release of GyLiber's controlled adversarial security assurance companion.

## What this release proves

v0.1.0 establishes a bounded end-to-end assurance loop:

```text
versioned target + campaign
        ↓
kill-switch + safety budgets
        ↓
Target Gate / resolved-address policy
        ↓
bounded HTTP HEAD probe
        ↓
PASS / FAIL oracle
        ↓
metadata-only evidence
        ↓
SHA-256 integrity seal
        ↓
checksummed JSON + human run bundle
```

The repository-controlled adversarial fixture laboratory proves in CI:

- secure fixture → **PASS**;
- vulnerable fixture → **FAIL**;
- fixed fixture → **PASS**.

## Operator interface

The release provides `intruder target validate`, `intruder campaign validate`, `intruder campaign plan`, `intruder run`, and `intruder kill-switch-status`. There is intentionally no normal arbitrary-target `scan <url>` command.

## Security boundaries

Only `HTTP_HEAD_STATUS` is armed. Release execution is IP-literal only. Hostname/DNS execution remains unarmed. Redirects and retries are disabled. Ambient proxy inheritance is disabled. Production private-network enrollment is rejected. Cloud metadata endpoints are denied. Evidence excludes response bodies and HTTP header values. The tool holds no Command Center production master credential.

## Release artifacts

The GitHub release contains a Linux x86_64 binary, packaged Linux x86_64 archive with schemas/examples/docs, CycloneDX JSON SBOM, and SHA-256 checksum manifest. The release pipeline also creates GitHub build-provenance and binary-SBOM attestations.

## Known limitations

Not yet armed: signed target/campaign registries; digital evidence signatures and signer trust; hostname/DNS-rebinding-safe connection execution; redirect re-authorization; authentication/session campaigns; authorization/API campaigns; detection/containment/recovery campaigns; scheduled continuous assurance; production Command Center testing; confidential durable evidence storage; and non-Linux-x86_64 prebuilt binaries.

## Data posture

v0.1.0 uses synthetic/security-test data only. No real client credentials, banking records, staff data, production sessions, or production database master credentials are required.

## Release trust evidence

Publication is blocked until the exact release-request commit passes the repository's normal CI and Security workflows. The release build independently repeats formatting, compilation, strict Clippy, and the full workspace test suite before packaging.
